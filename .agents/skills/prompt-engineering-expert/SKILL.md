# مهارة: خبير هندسة البرومبتات (Prompt Engineering Expert)

> هذه المهارة لا تُستبدل كل مرة — هي مرجع دائم يُقرأ ويُستخدم. مبنية على
> بحث فعلي في مصادر رسمية بتاريخ 2026 (وليس قوائم "أفضل 50 برومبت" من
> مقالات سطحية). المصادر الدقيقة مذكورة تحت كل قسم.

## المستوى 1-2: الأساسيات والتقنيات المتقدمة

### Zero-Shot vs Few-Shot
مصدر: Google Gemini — Prompt design strategies (ai.google.dev/gemini-api/docs/prompting-strategies).
- Zero-shot = بدون أمثلة، يعتمد على وضوح التعليمة وحدها.
- Few-shot = أمثلة متنوعة ومحدَّدة تُستخدم لضبط الصيغة/النطاق/النمط —
  استخدمها عندما يحتاج المخرج شكلاً دقيقًا متكررًا (JSON، جدول، نبرة
  معينة) لا تستطيع التعليمة النصية وحدها ضمانه.
- لا تستخدم أمثلة عشوائية: "استخدم أمثلة محددة ومتنوعة لتضييق تركيز
  النموذج" (المصدر نفسه).

### Be Clear and Direct (أهم تقنية مفردة حسب Anthropic)
مصدر: Anthropic — docs.claude.com/en/docs/build-with-claude/prompt-engineering/overview.
التقنيات مرتّبة رسميًا من الأوسع تأثيرًا للأكثر تخصصًا:
1. Prompt generator / تحسين تلقائي
2. وضوح ومباشرة
3. أمثلة (multishot)
4. السماح للنموذج بالتفكير (CoT)
5. وسوم XML
6. الأدوار (System Prompts)
7. Prefill الاستجابة
8. تسلسل البرومبتات المعقدة (Chaining)
9. نصائح السياق الطويل

### قاعدة خاصة بنماذج التفكير الحديثة (Gemini 3.x / الاستدلال)
مصدر: Google — "Gemini 3 developer guide" وتحديث Gemini 3.5 Flash.
**نماذج التفكير (reasoning models) تُفرط في تحليل البرومبتات المطوَّلة
المصممة للنماذج القديمة.** مع Gemini 3.x: تعليمات دقيقة ومختصرة أفضل من
CoT يدوي مطوَّل؛ اضبط verbosity صراحة إن أردت أسلوبًا محادثاتيًا (الوضع
الافتراضي مباشر ومقتضب). هذا يعني: **التقنية المناسبة تعتمد على النموذج
المستهدف، لا توجد وصفة واحدة تناسب الجميع.**

## المستوى 3: System Prompts و Meta Prompts
مصدر: OpenAI — Model Spec, chain_of_command (model-spec.openai.com).
- الأدوار لها **تراتبية سلطة**: `developer`/`system` > `user` > مخرجات
  أدوات سابقة. لا تضع نصًا غير موثوق في رسالة developer — هذا يمنحه أعلى
  صلاحية ممكنة (راجع مهارة `prompt-injection-defense`).
- System Prompt جيد = هوية + صلاحيات + حدود + تنسيق مخرجات، وليس سردًا
  طويلاً. مثال فعلي مُختبر من Anthropic: "You are a senior code reviewer.
  Analyze the provided code for bugs, security issues, and performance
  problems" + قيود صريحة (`Focus on logic errors, not style`) + تنسيق
  مخرجات محدد (JSON schema).

## المستوى 4: Chain of Thought وReasoning Guidance
مصدر: Anthropic — نفس الدليل أعلاه، قسم "Let Claude think".
ثلاثة مستويات فعلية (مُختبرة، ليست نظرية):
1. **Basic CoT**: "فكّر خطوة بخطوة" فقط.
2. **Guided CoT**: تحديد مراحل تفكير محددة بالترتيب.
3. **Structured CoT**: فصل التفكير عن الإجابة النهائية بوسوم (`<thinking>`
   ... `<answer>`).
ملاحظة مهمة: مع النماذج التي تملك "extended thinking" مدمجًا (Claude 4.x
بوضع adaptive، Gemini 3 بـthinking_level)، الـCoT اليدوي المطوّل أقل
فائدة وأحيانًا يُربك النموذج — فعّل التفكير المدمج أولاً، واستخدم CoT
اليدوي فقط حين لا يتوفر أو تحتاج شفافية تفكير قابلة للمراجعة.

## المستوى 5: Few-Shot وZero-Shot (تفصيل القرار)
معيار اختيار موثّق (Anthropic):
1. هل الطلب واضح وصريح؟ لا ⇒ أصلح الوضوح أولاً قبل أي تقنية أخرى.
2. المهمة بسيطة؟ ⇒ تقنيات أساسية فقط (تحديد، وضوح، سياق).
3. تحتاج تنسيقًا محددًا؟ ⇒ أمثلة أو Prefill.
4. معقدة؟ ⇒ فكّك لعدة برومبتات متسلسلة (Chaining).
5. تحتاج استدلالاً؟ ⇒ Extended thinking إن توفر، وإلا CoT.

## المستوى 6: Agentic Prompt Engineering
مصدر: Anthropic — "Building effective agents" (anthropic.com/research/building-effective-agents، ديسمبر 2024، المرجع الأكثر استشهادًا في المجال).
ثلاثة مبادئ ذهبية موثّقة:
1. **البساطة** — لا تبنِ معمارية معقدة إن كفى برومبت واحد مباشر.
2. **الشفافية** — اجعل خطوات التخطيط ظاهرة وقابلة للمراجعة (هذا بالضبط
   سبب استخدامنا لـ`STRATEGY_LOG.md` في مشروع MT5 — تطبيق مباشر لهذا
   المبدأ).
3. **واجهة الوكيل-الحاسوب (ACI)** — وثّق الأدوات واختبرها بنفس عناية
   توثيق الكود لمطوّر بشري.

نمطان معماريان موثّقان للمهام المعقدة:
- **Orchestrator-Workers**: نموذج مركزي يفكك المهمة ويوزّعها على عمّال،
  ثم يدمج النتائج. (هذا نمط Antigravity's Agent Manager بالضبط).
- **Evaluator-Optimizer**: نموذج يولّد، وآخر (أو نفسه بدور مختلف) يقيّم
  ويصحح في حلقة. (هذا نمط حلقة Arena↔Antigravity↔GitHub في مشروع MT5 —
  أنا المقيّم، Antigravity المولِّد، البيانات الحقيقية هي معيار التقييم).

## المستوى 7: Tool Calling وMCP Prompting
مصدر: Anthropic — "Writing effective tools for agents" + "Advanced tool use".
قواعد مُختبرة فعليًا بأرقام حقيقية من تجارب Anthropic الداخلية:
- وصف الأداة يحتاج: متى تُستخدم، المعاملات، المخرج المتوقع، حالات حافة.
  3-4 جمل على الأقل.
- إضافة `input_examples` للمعاملات الغامضة رفعت الدقة من **72% إلى 90%**
  في اختبارات Anthropic الداخلية — هذا رقم حقيقي موثّق وليس تقديرًا.
- استخدم مسارات مطلقة لا نسبية في أدوات الملفات (درس مستفاد من SWE-bench:
  النموذج يخطئ بالمسارات النسبية بعد تغيير المجلد — المسار المطلق يحسم
  المشكلة كليًا بدل تحسينها جزئيًا).
- اجعل رسائل الخطأ عملية وقابلة للتصرف (retry hint + مثال مصغّر)، لا
  رسالة خطأ عامة.
- هذا يطابق تمامًا ما طبّقناه فعليًا في `mcp-mt5-safe-execution` و
  `mt5-data-sync` في هذا المشروع (فحوصات إلزامية، رسائل خطأ حرفية غير
  ملخَّصة، لا إعادة محاولة عشوائية).

## طريقة عملي عند أي طلب برومبت مستقبلي (ثابتة، لا تتغير)
1. أفهم النتيجة النهائية المطلوبة فعليًا — أسأل إن كانت غامضة بدل التخمين.
2. أحدد النموذج/الوكيل المستهدف (Antigravity؟ Claude؟ GPT؟ Gemini؟) —
   كل واحد له أسلوب مختلف موثّق أعلاه.
3. أفحص الأدوات والصلاحيات المتاحة فعليًا لهذا الوكيل (لا أفترض).
4. أختار التقنية المناسبة من المستويات أعلاه حسب تعقيد المهمة.
5. أكتب البرومبت.
6. أقيّمه فعليًا عبر `PROMPT_QUALITY_RUBRIC.md` قبل التسليم — ليس حكمًا
   نظريًا، بل تطبيق المعايير العشرة رقميًا.
7. أُصلح نقاط الضعف المكتشفة (خصوصًا مقاومة حقن التعليمات — أضعف نقطة
   تتكرر في برومبتاتنا السابقة، راجع التقرير).
8. أسلّم النسخة النهائية جاهزة للنسخ المباشر، مع ملخص قصير لماذا صُمِّمت
   هكذا.
